# ActiveRecall ユーザーストーリーマップ

**作成日**: 2026-03-05
**開発方式**: ストーリー駆動開発（Story-Driven Development）
**原則**: ユーザーのユースケース（ストーリー）を起点にし、各ストーリーの前提条件を明確化して依存順序で開発する

## 再利用可能基盤: Voice Recording (US-VR)

### US-VR-001: 音声録音

**As a** ユーザー
**I want to** ブラウザ上で音声を録音し、録音した音声をファイルとして保存できる
**So that** 自分が話した内容を後で活用（文字起こし・分析等）できる

#### 前提条件
- なし（独立した基盤機能）

#### ユースケースシナリオ
1. ユーザーは録音コンポーネントが配置された画面を開く
2. 「録音開始」ボタンを押下する
3. ブラウザがマイクアクセスの許可を求める（初回のみ）
4. 許可後、録音が開始される（録音中であることが視覚的にわかる）
5. ユーザーはマイクに向かって話す
6. 話し終わったら「録音停止」ボタンを押下する
7. 録音された音声がファイルとしてバックエンドに保存される
8. 保存完了の通知が表示される

#### 受け入れ基準
- [ ] 録音開始ボタンを押すと、ブラウザのマイクアクセス許可ダイアログが表示される
- [ ] 録音中は視覚的なインジケーター（波形 or 赤い点滅 or 経過時間）が表示される
- [ ] 録音停止ボタンを押すと録音が終了する
- [ ] 録音した音声がバックエンドに送信・保存される（WAV or WebM形式）
- [ ] マイクアクセスが拒否された場合、エラーメッセージが表示される
- [ ] 録音時間の上限を設ける（例: 10分）
- [ ] ダークモード対応

#### 再利用ポイント
この録音コンポーネントは以下の場面で再利用可能:
- ActiveRecall（知識のアウトプット録音）
- アイディア壁打ち（音声メモ）
- タスクの洗い出し（口頭ブレスト）
- 議事録作成

#### 技術メモ
- **フロントエンド**: Web Audio API / MediaRecorder API
- **音声形式**: WebM（ブラウザネイティブ）→ バックエンドで必要に応じてWAV変換
- **保存先**: `backend/uploads/{user_id}/recordings/`（既存 multer パターン流用）
- **コンポーネント**: `VoiceRecorder.js`（再利用可能な汎用コンポーネント）

### US-VR-002: 音声文字起こし

**As a** ユーザー
**I want to** 録音した音声を自動で文字起こしし、テキストとして画面に表示できる
**So that** 話した内容をテキストとして確認・活用できる

#### 前提条件
- **US-VR-001** が完了していること（音声ファイルが保存されていること）

#### ユースケースシナリオ
1. 音声録音が完了した後、自動的に文字起こし処理が開始される
2. 処理中はローディングインジケーターが表示される（「文字起こし中...」）
3. 文字起こしが完了すると、結果テキストが画面に表示される
4. ユーザーは文字起こし結果を確認できる

#### 受け入れ基準
- [ ] 録音完了後、自動で文字起こしが開始される
- [ ] 文字起こし処理中はローディング表示がある
- [ ] 文字起こし結果がテキストとして画面に表示される
- [ ] 日本語の音声が正しく文字起こしされる
- [ ] 文字起こし失敗時にエラーメッセージが表示される
- [ ] 処理時間の目安が表示される（任意）

#### 再利用ポイント
文字起こしAPIは汎用的なエンドポイントとして設計:
- `POST /api/transcribe` — 音声ファイルを受け取りテキストを返す
- ActiveRecall以外のコンテキストからも呼び出し可能

#### 技術メモ
- **文字起こしエンジン**: `faster-whisper 1.2.1`（ローカルWSL環境に導入済み）
  - 仮想環境: `/home/phalanchang/clawd/.venv-whisper/`
  - モデル: `Systran/faster-whisper-small`（キャッシュ済み）
  - デバイス: CPU（`int8` compute type）
- **呼び出し方式**: バックエンド(Express)から子プロセスでPythonスクリプトを実行、または FastAPI等の別サービスとして起動
- **注意**: CPU版のため処理時間がかかる（1分の音声 → 数十秒〜数分）。UIでの待ち時間表示が重要

### US-VR-003: 文字起こし結果の整形

**As a** ユーザー
**I want to** 文字起こしの生テキストを、「おそらくこう話していたであろう」読みやすい文章に整形できる
**So that** 文字起こしの認識ミスやフィラー（えーと、あの）を除去し、内容を正確に把握できる

#### 前提条件
- **US-VR-002** が完了していること（文字起こしテキストが取得できること）

#### ユースケースシナリオ
1. 文字起こしが完了し、生テキストが画面に表示される
2. システムが自動的にAIによる整形処理を実行する
3. 整形処理中はローディングインジケーターが表示される
4. 整形後のテキストが、生テキストと並べて（or 切替で）表示される
5. ユーザーは整形結果を確認し、必要に応じて手動で修正できる

#### 受け入れ基準
- [ ] 文字起こし完了後、AIによる整形が自動実行される
- [ ] フィラー（えーと、あの、まあ）が除去される
- [ ] 認識ミスと思われる箇所が修正される
- [ ] 文章として自然な形に整形される（句読点、段落分け）
- [ ] 生テキストと整形テキストの両方を確認できる
- [ ] 整形テキストを手動で修正できる（編集可能テキストエリア）

#### 技術メモ
- **整形エンジン**: Claude API（Anthropic Messages API）
- **プロンプト**: 「以下の文字起こしテキストを、話者が実際に伝えたかった内容に整形してください。フィラーの除去、認識ミスの修正、句読点の追加を行い、自然な日本語の文章にしてください。」
- **バックエンド**: `POST /api/transcribe/refine` — 生テキストを受け取り整形テキストを返す

## 知識インプット: Knowledge Input (US-KI)

### US-KI-001: 知識テーマの登録

**As a** ユーザー
**I want to** 学習したいテーマを登録・管理できる
**So that** ActiveRecallの対象となる知識体系を整理できる

#### 前提条件
- なし（独立した基盤機能）

#### ユースケースシナリオ
1. ユーザーは「学習テーマ一覧」ページを開く
2. 「新規テーマ追加」ボタンを押す
3. テーマのタイトルを入力する（例: 「AI駆動開発とストーリー駆動開発について」）
4. カテゴリを選択する（技術 / 業務 / 語学 / 資格 / その他）
5. 保存ボタンを押すと、テーマが一覧に追加される
6. 一覧では各テーマの状態が確認できる（コンテンツ未作成 / 作成済み / リコール済み）

#### 受け入れ基準
- [ ] テーマ一覧画面が表示される（`/knowledge`）
- [ ] 新規テーマを追加できる（タイトル必須、カテゴリ任意）
- [ ] テーマを編集・削除できる
- [ ] テーマごとの状態（コンテンツ有無、リコール回数）が表示される
- [ ] カテゴリでフィルタリングできる
- [ ] ダークモード対応
- [ ] アイコン付きのコンパクトなUI（テーマ名が長くなるため）

#### 技術メモ
- **DB**: `knowledge_themes` テーブル（id, user_id, title, category, created_at, updated_at）
- **API**: `GET/POST/PUT/DELETE /api/knowledge/themes`
- **UI**: 既存 WishList パターンを踏襲（テーブル or カードビュー）

### US-KI-002: 知識コンテンツの作成

**As a** ユーザー
**I want to** テーマに対して、複数の記事や資料を参照してまとめた知識コンテンツ（キーワード、ポイント、フロー等）を作成・保存できる
**So that** ActiveRecallの採点基準となるリファレンス資料を準備できる

#### 前提条件
- **US-KI-001** が完了していること（テーマが登録されていること）

#### ユースケースシナリオ
1. ユーザーはテーマ一覧から対象テーマをクリックする
2. テーマの詳細画面が開く
3. 「知識コンテンツ」セクションで内容を編集する
4. テーマに沿ったキーワード、ポイント、フロー、重要な概念をテキストで記述する
5. 保存ボタンを押すと内容が保存される
6. いつでも再編集が可能

#### 受け入れ基準
- [ ] テーマ詳細画面で知識コンテンツを編集できる
- [ ] テキストエリアで自由記述できる（マークダウン対応推奨）
- [ ] 保存・更新ができる
- [ ] コンテンツの更新履歴が確認できる（更新日時の表示）
- [ ] コンテンツが未作成のテーマには「コンテンツ未作成」の表示がある

#### 技術メモ
- **DB**: `knowledge_contents` テーブル（id, theme_id, user_id, content TEXT, created_at, updated_at）
- **API**: `GET/PUT /api/knowledge/themes/:themeId/content`
- **UI**: 大きなテキストエリア、プレビュー表示（マークダウン対応時）

## ActiveRecall: アクティブリコール (US-AR)

### US-AR-001: ActiveRecallセッション開始

**As a** ユーザー
**I want to** ActiveRecallページでテーマを選択し、録音を通じて知識のアウトプットを行える
**So that** 自分の記憶からテーマに関する知識を引き出す訓練ができる

#### 前提条件
- **US-KI-002** が完了していること（テーマに知識コンテンツが存在すること）
- **US-VR-001** が完了していること（音声録音機能が使えること）

#### ユースケースシナリオ
1. ユーザーはActiveRecallページ（`/active-recall`）を開く
2. 知識コンテンツが作成済みのテーマが一覧表示される（アイコン付き）
3. テーマを1つ選択する
4. ActiveRecall開始ボタン（アイコン: 🎯 or ▶️）を押下する
5. 録音画面に遷移する
6. 「録音開始」ボタンを押下して、テーマに関する知識をマイクに向かって話す
7. 話し終わったら「録音停止」ボタンを押下する
8. 音声ファイルが保存され、文字起こし処理が開始される

#### 受け入れ基準
- [ ] ActiveRecallページにテーマ一覧が表示される（コンテンツ作成済みのみ）
- [ ] 各テーマにアイコン付きの開始ボタンがある（テキスト不要のコンパクトUI）
- [ ] テーマ選択後に録音画面が表示される
- [ ] 選択中のテーマ名が録音画面上部に表示される（ただし知識コンテンツは非表示=カンニング防止）
- [ ] 録音→停止→文字起こし開始が一連の流れで動作する
- [ ] ダークモード対応

#### 技術メモ
- **UI**: テーマカードまたはリスト形式。開始ボタンはアイコンのみ（🎯 / ▶️ / 🎤）
- **制約**: 録音中はテーマのコンテンツを見せない（ActiveRecallの本質は「見ないで思い出す」）
- **DB**: `recall_sessions` テーブル（id, theme_id, user_id, audio_path, started_at, completed_at）

- [ ] 整形テキストは編集可能（手動修正対応）

- [ ] ダークモード対応

### US-AR-003: AI比較採点

**As a** ユーザー
**I want to** 自分のリコール内容（整形テキスト）をテーマの知識コンテンツと比較し、AIに採点してもらえる
**So that** 知識の正確性と網羅性を客観的に把握できる

#### 前提条件
- **US-AR-002** が完了していること（リコール結果テキストが確定していること）
- **US-KI-002** が完了していること（比較対象の知識コンテンツが存在すること）

#### ユースケースシナリオ
1. ユーザーが「採点に進む」ボタンを押す
2. システムが以下の比較処理を実行する:
   a. リコール内容（整形テキスト）をAIに送信
   b. テーマの知識コンテンツ（リファレンス）もAIに送信
   c. AIが以下を分析する:
      - **正確性**: リコール内容に誤った知識がないか
      - **網羅性**: 知識コンテンツのうち、話さなかった内容はないか
      - **構造性**: 論理的な順序で説明できていたか
      - **具体性**: 具体例やキーワードを適切に使えていたか
3. 処理中はローディング表示（「AI採点中...」）
4. 採点完了後、結果画面に遷移する

#### 受け入れ基準
- [ ] リコール内容と知識コンテンツの比較がAIで実行される
- [ ] 採点は複数の観点で行われる（最低4観点）
- [ ] 各観点ごとにスコア（0-100 or 5段階）が算出される
- [ ] 総合スコアが算出される
- [ ] 誤った知識が具体的に指摘される（該当箇所 + 正しい内容）
- [ ] 話さなかった内容が具体的にリストアップされる
- [ ] 採点処理中にローディング表示がある

#### 採点観点（案）

| 観点 | 評価内容 | 配点 |
|------|---------|------|
| 正確性（Accuracy） | 誤った知識・事実誤認がないか | 30点 |
| 網羅性（Coverage） | リファレンスの重要ポイントをどれだけカバーしたか | 30点 |
| 構造性（Structure） | 論理的な順序・体系で説明できているか | 20点 |
| 具体性（Specificity） | キーワード・具体例・数値を適切に使えているか | 20点 |
| **総合** | | **100点** |

#### 技術メモ
- **AIエンジン**: Claude API（Anthropic Messages API）
- **プロンプト設計**: リファレンスとリコールの2テキストを渡し、4観点で構造化JSONを返させる
- **バックエンド**: `POST /api/active-recall/sessions/:sessionId/score`
- **DB**: `recall_scores` テーブル（session_id, accuracy, coverage, structure, specificity, total, feedback_json）

### US-AR-004: フィードバック・スコア表示

**As a** ユーザー
**I want to** 採点結果を視覚的に確認し、具体的なフィードバック（誤り・不足）を把握できる
**So that** 知識の弱点を特定し、次の学習に活かせる

#### 前提条件
- **US-AR-003** が完了していること（採点結果が存在すること）

#### ユースケースシナリオ
1. 採点完了後、フィードバック画面が表示される
2. 画面上部に総合スコア（100点満点）が大きく表示される
3. 4観点の個別スコアがレーダーチャートまたはバーで表示される
4. 「誤った知識」セクションに、誤り箇所と正しい内容が対比表示される
5. 「話さなかった内容」セクションに、不足していたポイントがリスト表示される
6. 「良かった点」セクションに、正しく想起できたポイントが表示される
7. ユーザーは結果を確認し、「テーマ一覧に戻る」または「もう一度リコール」を選択できる

#### 受け入れ基準
- [ ] 総合スコア（100点満点）が大きく表示される
- [ ] 4観点の個別スコアが視覚的に表示される（チャート or バー）
- [ ] 「誤った知識」が具体的に表示される（何が間違っていて、正しくは何か）
- [ ] 「話さなかった内容」がリスト表示される
- [ ] 「良かった点」がリスト表示される
- [ ] セッション履歴として結果が保存される
- [ ] 「テーマ一覧に戻る」「もう一度リコール」ボタンがある
- [ ] 過去のスコア推移が確認できる（将来拡張: US-AR-005）
- [ ] ダークモード対応

#### 技術メモ
- **チャート**: Recharts（既存ライブラリ）でレーダーチャート or バーチャート
- **保存**: 各セッションの結果をDBに保存し、テーマ別のスコア推移を追跡

## 実装優先順序（推奨）

```
Phase 1: 再利用可能基盤
  US-VR-001 → US-VR-002
  （音声録音 → 文字起こし）

Phase 2: 知識管理
  US-KI-001 → US-KI-002
  （テーマ登録 → コンテンツ作成）

Phase 3: ActiveRecallコア
  US-AR-001 → US-AR-002 → US-VR-003 → US-AR-003 → US-AR-004
  （セッション開始 → 結果表示 → 整形 → 採点 → フィードバック）
```

※ Phase 1 と Phase 2 は独立しているため並行開発可能
